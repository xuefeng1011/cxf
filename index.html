실무 경험의 문제를 모델링

01. 코스를 동시에 편집하면 왜 위험할까?

확인된 실제 경험
러닝빌더에서 같은 코스를 여러 관리자가 동시에 편집해 서로의 변경을 덮는 상황을 방지하려고 낙관적 잠금을 사용했고, JPA Dirty Checking도 활용했습니다. 아래 v7·v8과 HTTP 요청은 학습용 가상 값입니다.

관리자 A와 B가 같은 코스 Java 기초 과정(v7)을 열고 각각 제목을 수정합니다.

👨‍💻 관리자 B

읽은 버전: v7
새 제목: Java 입문 과정

02. Dirty Checking vs @Version

Dirty Checking은 영속 상태 변경을 Flush할 때 DB에 반영하는 메커니즘입니다. @Version은 변경 시 이전 버전이 유지돼 있는지 확인해 충돌을 감지합니다.

@Entity
class CourseJpaEntity {
  @Id Long id;
  @Version Long version;
  String title;

  void rename(String title) {
    if (title == null || title.isBlank())
      throw new IllegalArgumentException("제목 필수");
    this.title = title;
  }
}
@Transactional
public long edit(long id, long expectedVersion, String title) {
  CourseJpaEntity course = repo.findById(id).orElseThrow();

  // 오래된 웹 화면의 버전을 따로 검증
  if (!Objects.equals(course.version, expectedVersion))
    throw new StaleCourseEditException();

  course.rename(title); // Dirty Checking 대상
  repo.flush();         // @Version 충돌 검사
  return course.version;
}
실제 예제에서는 필드 접근자, Repository, 예외 클래스 등 일부 보일러플레이트를 생략했습니다. Flush는 Commit이 아닙니다. 낙관적 잠금이 충돌하면 트랜잭션은 롤백됩니다.

SQL로 보는 핵심

UPDATE course
SET title = 'Java 실무 과정', version = 8
WHERE id = 100 AND version = 7;

-- A: 1건 성공, version 8
-- B: 같은 version 7로 UPDATE 시 0건 → 충돌

실제 테스트에서 확인할 것

테스트예상 결과
예전 화면 v7으로 저장, DB v8StaleCourseEditException
두 트랜잭션이 같은 v7 읽고 업데이트하나만 성공, 다른 쪽 충돌
중간에 오류 발생트랜잭션 전체 롤백
자식 Lesson만 수정부모 Course 버전 자동 증가 여부 확인 필요
@Test
void 오래된_편집은_저장할수없다() {
  // 독립 트랜잭션을 사용하는 통합 테스트 전제
  long v7 = loadVersion(100L);
  service.edit(100L, v7, "Java 실무 과정"); // v8
  assertThrows(StaleCourseEditException.class,
      () -> service.edit(100L, v7, "Java 입문 과정"));
  assertEquals("Java 실무 과정", loadTitle(100L));
}

병렬 트랜잭션 충돌 자체는 CountDownLatch + 독립 트랜잭션 + PostgreSQL(Testcontainers)로 별도 검증하세요. 위 코드는 설명용 테스트 골격입니다.

DDD 사고법

03. Aggregate 경계를 왜 정해야 할까?

코스 전체 편집 규칙이 하나의 일관성 경계라면 Course가 Aggregate Root가 될 수 있습니다. 하지만 서로 독립인 차시 편집까지 코스 전체로 잠그면 불필요한 충돌이 늘어납니다.

코스 전체가 하나의 충돌 경계
Course v7
↓
Lesson 1 · 2 · 3
↓
전체 구성·발행 규칙 보호
차시별 독립 버전
Lesson 1 v3
↕
Lesson 3 v5
↓
독립 편집 충돌 감소
JPA 함정: Lesson이 별도 엔티티라면 자식의 필드 수정이 부모 Course.version을 자동으로 증가시키지 않을 수 있습니다. 전체 코스의 보호가 목표라면 부모 버전 증가를 명시적으로 보장해야 합니다.
entityManager.lock(
  courseEntity,
  LockModeType.OPTIMISTIC_FORCE_INCREMENT
);

이 선택은 동시 편집 편의성과 전체 코스 정합성의 균형입니다. 차시 순서, 필수 학습 구성, 발행 조건을 하나의 규칙으로 보호해야 하는지에 따라 경계가 바뀝니다.

면접 질문: Aggregate는 왜 필요하나요?

함께 일관되게 지켜야 하는 비즈니스 불변식의 경계를 정하기 위해서입니다. 코스 발행 조건처럼 여러 차시에 걸친 규칙을 어디서 최종 검증할지 명확하게 만듭니다.

Clean Architecture

04. 계층 분리와 로직 오염 방지

Controller 안에 발행 규칙, JPA 쿼리, 이벤트 전송이 모두 섞이면 변경 이유가 서로 다른 코드가 한 곳에 모입니다. 비즈니스 규칙이 기술 구현에 끌려다니지 않도록 의존성을 설계합니다.

CQRS 사고법

05. 코스 편집과 목록 조회가 왜 달라야 할까?

Command는 코스 수정 규칙을 지키고, Query는 화면에 필요한 데이터만 읽습니다. 두 작업의 목적이 다르기 때문에 같은 모델을 강제로 사용할 필요가 없습니다.

Write · Command
EditCourseUseCase
↓
Course.rename()
↓
JPA @Version 검사
Read · Query
GetCourseList
↓
CourseListDto Projection
↓
빠른 목록 응답
// Command: 규칙을 지키면서 상태 변경
course.rename("Java 실무 과정");

// Query: 목록에 필요한 필드만 반환
SELECT new CourseListDto(c.id, c.title, c.status)
FROM CourseJpaEntity c
CQRS는 Kafka, Event Sourcing, 별도 Read DB가 없어도 적용할 수 있습니다. 한 PostgreSQL에서 읽기와 쓰기 모델만 구분하는 것이 가장 쉬운 시작입니다.
실무 면접 대비

06. 설계 이유를 답할 수 있어야 한다

30~60초 답변 예시
“휴넷 CMS 3.0 러닝빌더에서 여러 관리자가 하나의 코스를 동시에 수정할 수 있었습니다. 나중에 저장한 변경이 먼저 저장된 내용을 덮어쓰는 위험을 줄이기 위해 낙관적 잠금을 사용했습니다. JPA 변경 감지로 영속 엔티티 수정 내용을 저장하고, 버전 기반 충돌 감지로 데이터 정합성을 고려했습니다. 이 방식은 편집 시간 내내 DB 잠금을 유지하지 않으면서 저장 시 충돌을 확인할 수 있다는 장점이 있습니다. 다만 코스와 차시의 충돌 범위를 어디까지 볼지는 Aggregate 경계와 함께 판단해야 합니다.”
Q1. Dirty Checking과 낙관적 잠금은 같은 기능인가요?

아닙니다. Dirty Checking은 변경 내용을 DB에 반영하고, 낙관적 잠금은 오래된 버전에 기반한 갱신 충돌을 감지합니다.

Q2. @Version을 붙였는데도 덮어쓰기가 발생할 수 있나요?

예. 오래된 브라우저 화면에서 저장할 때마다 서버가 최신 엔티티를 재조회한 후 이전 값을 복사하면 @Version 검사만으로 화면의 오래된 상태를 구별할 수 없습니다. 사용자가 처음 본 버전을 요청에 포함시켜 검사합니다.

Q3. 비관적 잠금 대신 낙관적 잠금을 선택한 이유는?

웹 편집 화면은 열어두는 시간이 길어 DB 락을 계속 점유하는 구조가 부담스럽습니다. 낙관적 잠금은 보통 충돌이 많지 않은 상황에서 저장 시점을 기준으로 감지하며, 발생한 충돌은 사용자에게 안내해 해결합니다.

Q4. Course와 Lesson 중 어느 쪽을 Aggregate로 만드나요?

하나의 트랜잭션에서 반드시 함께 지켜야 하는 불변식을 기준으로 정합니다. 전체 차시 순서와 발행 규칙은 코스 차원의 판단이 필요할 수 있지만, 독립 편집이 많다면 충돌 범위를 잘게 나누는 설계도 고려합니다.

Q5. Clean Architecture와 DDD, CQRS는 각각 무엇인가요?

DDD는 업무 모델과 불변식의 경계를, Clean Architecture는 기술로부터 비즈니스 코드의 의존성을 보호하는 구조를, CQRS는 상태 변경과 읽기 목적의 모델 분리를 담당합니다.
