CHAPTER 01 실무 문제 출발

낙관적 잠금 · 덮어쓰기를 막는 설계

상황: 관리자가 하나의 코스를 오랫동안 편집합니다. 같은 코스를 다른 관리자가 수정하고 먼저 저장하면, 나중에 저장하는 사람의 오래된 입력이 기존 변경을 덮을 수 있습니다.

위험한 흐름

A와 B가 모두 v7 조회 → A가 제목 수정 저장 → B가 이전 화면의 제목을 저장 → A 변경 손실

설계 목표

편집 중에 DB 락을 오래 유지하지 않으면서, 저장 시점에 이전 버전과의 충돌을 검증해 조용한 덮어쓰기를 막습니다.

1-1. 직접 문제를 재현하세요

아래는 실제 DB가 아니라 원리를 설명하는 브라우저 시뮬레이션입니다.

👩 관리자 A

열어본 코스: v7
수정할 제목: Java 실무 과정

👨 관리자 B

열어본 코스: v7
수정할 제목: Java 입문 과정

시작 · 두 관리자가 v7 조회
Java 기초 과정
DB version 7
① A 저장을 눌러 진행해 보세요.
중요: @Version만으로 모든 웹 편집이 안전해지지 않습니다.
서버가 매 HTTP 저장 요청마다 최신 엔티티를 읽고 오래된 화면 값을 적용하면, JPA는 그것을 정상적인 새 변경으로 취급할 수 있습니다. 편집 시작 시점의 버전을 클라이언트에서 보내고 비교하는 방식을 함께 고려해야 합니다.

1-2. 왜 둘의 역할이 다를까?

기능무엇을 하는가무엇을 자동으로 보장하지 않는가
Dirty Checking영속 엔티티의 변경을 Flush 시 SQL로 반영브라우저의 오래된 작업 감지
JPA @Version읽은 버전에 기반한 동시 DB UPDATE 충돌 검사최신 엔티티를 재조회한 뒤 이전 화면 값을 적용하는 실수
expectedVersion 검증편집 시작 당시 화면 버전과 현재 DB 버전 비교검사 직후 또 다른 트랜잭션이 수정하는 경쟁 상태
두 검증 함께오래된 화면 + 동시 DB 경합 모두 검사충돌 후 자동 병합이나 사용자 경험까지 해결하지는 않음

1-3. 코드를 아주 작게 나눠 이해

① JPA 엔티티
@Entity
class CourseJpaEntity {
  @Id Long id;
  @Version Long version;       // 동시 갱신 확인
  String title;

  void rename(String title) {  // 상태 변경
    if (title == null || title.isBlank())
      throw new IllegalArgumentException("제목 필수");
    this.title = title;
  }
}
② Application Service · 학습용 핵심 구현
@Transactional
public long edit(long id, long expectedVersion, String title) {
  CourseJpaEntity course = repo.findById(id).orElseThrow();
  if (!Objects.equals(course.getVersion(), expectedVersion))
    throw new StaleCourseEditException();

  course.rename(title); // Dirty Checking 대상
  repo.flush();         // SQL / @Version 충돌 확인
  return course.getVersion();
}

설명용 간소화 코드입니다. Repository, Getter, Exception 등 보일러플레이트는 생략했습니다. flush()는 Commit이 아니므로 이후 트랜잭션 실패 시 롤백됩니다.

③ UPDATE가 실제로 지키는 조건
UPDATE course
SET title = 'Java 실무 과정', version = 8
WHERE id = 100 AND version = 7;

-- A: 1행 UPDATE → version 8
-- B: 예전 version 7로 UPDATE → 0행 → 충돌

1-4. 놓치기 쉬운 여섯 가지 장애 상황

① 같은 코스 제목을 두 명이 동시에 수정

같은 v7을 읽은 별도 트랜잭션 두 개가 서로 다른 제목을 UPDATE하면 한쪽만 성공하도록 @Version 충돌을 검사합니다. 실패한 트랜잭션은 롤백되어야 합니다.

② 브라우저 화면을 10분 열어두고 저장

새 HTTP 요청의 트랜잭션은 최신 v8을 읽을 수 있으므로, 옛 화면의 expectedVersion=7을 추가로 검사해야 합니다. 보통 충돌 응답을 반환하고 변경 내용을 비교하게 합니다.

③ A는 1번, B는 3번 차시를 수정

부모 Course 단위 버전을 함께 증가시키면 의도적으로 충돌을 발생시킵니다. 서로 독립된 Lesson 버전을 쓰면 불필요한 충돌을 줄일 수 있지만 전체 코스 불변식 보호가 어려워집니다.

④ Lesson만 수정했는데 부모 Course 버전은 그대로

자식이 별도 엔티티인 경우 부모 버전이 자동 증가한다고 가정하지 마세요. 필요하면 부모 변경 경로에서 OPTIMISTIC_FORCE_INCREMENT 등 명시적 증가 정책을 검토합니다.

⑤ JPQL Bulk UPDATE를 직접 실행

일반적인 영속 엔티티 변경 감지와 버전 검사를 우회할 수 있습니다. Bulk UPDATE를 허용한다면 버전 조건, 영향 행 수, 영속성 컨텍스트 동기화를 별도로 처리해야 합니다.

⑥ 충돌 후 자동으로 다시 저장

무조건 재시도하면 사용자 B의 오래된 의도대로 A의 값을 결국 덮을 수 있습니다. 최신 값을 다시 보여주고 병합·재수정 여부를 사용자에게 묻는 정책이 필요합니다.

CHAPTER 02 실무에서 출발한 모델링 연습

DDD · 코스 규칙은 누가 책임질까?

문제: Controller, CourseService, ProductService 곳곳에 '발행 가능한 코스' 판단 규칙이 중복되면 한 곳만 고쳤을 때 모순이 생깁니다. DDD는 업무 용어와 규칙의 경계를 찾는 데 집중합니다.

업무 경계: 콘텐츠 제작

↓ 콘텐츠 참조

업무 경계: 제공·학습

↓ 발행 버전

용어 구분: CMS에서 편집 중인 Course와 학습자가 소비하는 PublishedCourse는 같은 '코스'라도 책임과 상태 규칙이 다를 수 있습니다. 위 경계는 학습용 모델링안입니다.

2-1. 먼저 비즈니스 규칙을 찾아보세요

코스 발행에는 차시가 필요Course Aggregate코스 전체 불변식
코스 ID 형식은 숫자Web AdapterHTTP 요청의 형식 검증
관리자에게 편집 권한이 있는가Application + 인가 정책행위자에 대한 권한 조율
발행본은 기존 학습자를 보호발행·학습 버전 정책시점과 도메인 간 계약 관리

2-2. Aggregate의 잠금 범위를 선택하세요

편집 실험: A=1번 차시, B=3번 차시
코스 전체 버전이 충돌
전체 차시의 일관성을 보호하는 대신, 서로 다른 차시를 수정해도 충돌이 날 수 있습니다.
설계의 균형: Aggregate가 지나치게 크면 경합과 로딩 비용이 증가하고, 너무 잘게 나누면 여러 객체에 걸친 불변식을 하나의 트랜잭션에서 보장하기 어려워집니다.
순수 Domain 객체: 발행 규칙만 보관
public final class CourseDraft {
  private String title;
  private List<Lesson> lessons;
  private boolean published;

  public void rename(String next) {
    if (next == null || next.isBlank())
      throw new InvalidCourseTitleException();
    if (published) throw new PublishedCourseEditException();
    title = next;
  }

  public void publish() {
    if (lessons.isEmpty()) throw new MissingLessonException();
    published = true;
  }
}

위 모델은 JPA·SQL·HTTP를 모릅니다. Domain이 보호하는 것은 "유효하지 않은 Course가 발행되지 않는다" 같은 업무 불변식입니다. 실제 완성 코드에는 생성 시점과 모든 변경 경로의 불변식도 보호해야 합니다.

DB version낙관적 잠금용
CourseVersion콘텐츠 발행본 식별
Product snapshot학습용 읽기 데이터
꼭 구분: JPA @Version의 동시성용 숫자와 콘텐츠의 비즈니스 발행 버전은 다릅니다. 이름이 'version'이라도 해결하는 문제가 다릅니다.

2-3. 면접에서 판단할 기준

Q. Course 안에 모든 Lesson을 넣는 것이 DDD인가요?

아닙니다. Aggregate는 단순한 객체 묶음이 아니라 단일 일관성 경계입니다. 전체 발행 규칙과 차시 편집 경합, 데이터 로딩 비용을 보고 범위를 결정해야 합니다.

Q. Entity와 Value Object는 무엇이 다른가요?

Entity는 고유 식별성과 생명주기가 중요합니다. Value Object는 값의 의미와 불변성이 중요합니다. 예를 들어 CourseId는 식별자 값 객체, LessonOrder는 순서 규칙을 캡슐화하는 값 객체로 모델링할 수 있습니다.

Q. Domain Event는 Kafka 이벤트와 같은가요?

Domain Event는 'CoursePublished' 같은 업무 사실을 표현합니다. Kafka는 이를 외부로 전달하는 기술적 수단 중 하나입니다. 모든 도메인 이벤트가 Kafka에 발행될 필요는 없습니다.

3-1. 나쁜 코드에서 어떤 문제가 보이나요?

@PutMapping("/course/{id}/publish")
public void publish(@PathVariable Long id) {
  var entity = jpaRepo.findById(id).orElseThrow();
  if (entity.getLessons().isEmpty()) throw new RuntimeException();
  entity.setPublished(true);  // 도메인 규칙
  jpaRepo.save(entity);       // 영속성
  kafkaTemplate.send("published", id); // 외부 전송
}

이 구조에서는 배치에서도 같은 발행 규칙을 재사용하려면 로직을 다시 작성할 위험이 있습니다. DB 방식이나 외부 이벤트 발행 정책 변경도 HTTP 계층을 흔듭니다.

3-2. 계층 책임과 의존성 화살표

유스케이스, 작업 순서, 트랜잭션

발행 불변식·상태 전이

Port

저장·연동에 필요한 계약

Test

Port는 내부 계층의 계약
public interface CourseRepository {
  CourseDraft load(long courseId);
  void save(CourseDraft course);
}

class PublishCourseUseCase {
  private final CourseRepository courses;

  @Transactional
  public void publish(long id) {
    CourseDraft draft = courses.load(id);
    draft.publish();            // 도메인 규칙
    courses.save(draft);        // 기술 구현 몰라도 됨
  }
}

3-3. 요구사항 변경 실험: 어떤 파일이 바뀌어야 할까?

DB 기술 변경
Persistence Adapter 중심
Domain의 발행 조건을 유지하면서 JPA 매핑과 Repository 구현을 MyBatis 구현으로 교체하도록 설계합니다.
반론도 알아야 합니다. 모든 CRUD에 Domain, Port, Adapter를 만들면 클래스와 변환 코드가 많아집니다. 복잡한 비즈니스 규칙, 장기 변경 비용, 팀 규모에 맞게 도입해야 합니다.

3-4. 설계가 지켜지는지 검증

@Test
void 모듈_의존성_규칙을_검증한다() {
  ApplicationModules.of(LmsApplication.class).verify();
}

Spring Modulith로 모듈 경계를 검사하거나 ArchUnit으로 Domain이 JPA·HTTP 패키지를 참조하지 못하게 규칙을 작성할 수 있습니다. 위 테스트는 Spring Modulith를 설정한 프로젝트에서 사용하는 예시입니다.

CHAPTER 04 CMS 버전 발행에서 확장한 설계 연습

CQRS · 쓰기 모델과 읽기 모델 분리

문제: 관리자의 코스 편집은 규칙 검증과 버전 관리가 필요하지만, 학습자가 코스를 조회할 때는 이미 발행된 빠르고 안정적인 형태의 데이터가 필요할 수 있습니다.

Command / 편집 경로

EditCourse / PublishCourse
↓

↓
발행본 생성

Query / 조회 경로

↓

↓
학습자가 버전 조회
실무와 가상 모델 구분: CMS 3.0에서 콘텐츠 버전과 Product API를 다룬 경험은 실제입니다. 아래 Draft → PublishedCourse → 읽기 전용 Projection을 'CQRS를 적용했다'고 단정하는 것은 아니며 이해를 위한 설계 예제입니다.

4-1. 발행 버전 실험

운영 중인 학습자에게는 v3가 고정돼 있고, 관리자는 v4 초안을 수정 중이라고 가정합니다.

버전 정책을 구분하세요: 모든 콘텐츠를 최신으로 조회할지, 학습 구조를 버전 고정할지, 일부 에셋만 최신 참조할지는 명시적인 업무 정책입니다. 위 시뮬레이션은 버전 고정 정책의 예입니다.

4-2. CQRS는 분산 시스템을 의미하지 않습니다

선택언제 적합한가문제점·주의사항
단일 모델 CRUD읽기와 쓰기가 단순할 때규칙과 화면 조회가 결합될 수 있음
단일 DB CQRS쓰기 규칙과 조회 최적화가 다를 때DTO·Query 서비스 코드 증가

쓰기 모델은 v4인데 읽기 모델은 v3에 남을 수 있습니다.

Transactional Outbox + 소비자 멱등성

같은 DB 트랜잭션에 이벤트 기록을 남겨 재전송을 가능하게 하고 중복 적용을 제어하는 설계를 고려합니다.

왜 바로 Kafka를 쓰지 않을까? 동일 DB의 Projection으로 충분한 경우라면 단순하게 유지합니다. 독립적인 서비스·처리량·비동기 요구가 확인될 때 이벤트 전달을 검토합니다.

4-4. 테스트할 정책

FINAL PRACTICE

면접에서 '왜 그 설계였나요?'에 답하는 법

실제 경험에 기반한 1분 답변
“휴넷 CMS 3.0 러닝빌더에서는 여러 관리자가 동일 코스를 동시에 편집할 수 있었습니다. 나중에 저장한 변경 내용이 먼저 저장된 작업을 덮어쓰는 위험을 줄이기 위해 낙관적 잠금을 적용했고, JPA 변경 감지로 엔티티의 수정 사항을 반영했습니다. 중요한 것은 어떤 기술을 썼다는 사실보다 여러 사용자의 변경이 충돌하는 상황에서 데이터 정합성을 고려했다는 점입니다. 또한 잠금 범위를 코스 전체로 볼지 차시별로 볼지는 업무 규칙과 동시 편집 방식에 따라 판단해야 합니다.”

꼬리질문 훈련

Q1. 왜 비관적 잠금이 아니라 낙관적 잠금이었나요?

웹 편집기에서는 화면을 열어두는 시간이 길기 때문에 그 기간 DB 잠금을 유지하는 방식은 부담이 큽니다. 저장 시점에 충돌을 확인하는 낙관적 잠금이 합리적인 후보입니다. 다만 실제 충돌 빈도와 UX를 고려해야 합니다.

Q2. @Transactional만 붙이면 Lost Update를 방지하나요?

아닙니다. 일반적인 트랜잭션만으로 모든 갱신 손실을 자동 차단할 수는 없습니다. 격리 수준과 DB 동시성 동작을 확인하고 버전 검사나 잠금·조건부 UPDATE를 설계해야 합니다.

Q3. Dirty Checking은 save()와 어떻게 다른가요?

Dirty Checking은 영속성 컨텍스트가 관리하는 엔티티의 상태 변경을 Flush할 때 UPDATE로 반영합니다. Spring Data JPA의 save()는 새 엔티티 등록 또는 merge 등 용도로 쓰이며, 이미 관리되는 엔티티를 수정한 경우 매번 save()가 필요한 것은 아닙니다.

Q4. Course의 @Version으로 모든 Lesson 수정이 보호되나요?

자식이 별도 엔티티라면 그렇지 않을 수 있습니다. 부모 버전 증가 정책과 Aggregate 일관성 경계를 명시해야 합니다.

Q5. DDD와 Clean Architecture의 차이는 뭔가요?

DDD는 업무 언어·모델·불변식의 경계를 정하고, Clean Architecture는 그 모델을 HTTP·DB 같은 기술 구현 의존성에서 보호하는 구조를 정합니다. 서로 다른 문제를 해결하므로 함께 활용할 수 있습니다.

Q6. CQRS는 Kafka와 별도 DB를 요구하나요?

아닙니다. 같은 DB를 사용하더라도 Query와 Command의 책임과 모델을 분리할 수 있습니다. 읽기 모델을 분리할 때만 동기화와 최종 일관성 문제를 추가로 다루면 됩니다.
